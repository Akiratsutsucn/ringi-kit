# 项目 A 领域知识：配置管理器部署与客户端铺装

本文件是项目 A「终端管理平台部署与客户端铺装」的领域参考。产品在文中称「配置管理器（Configuration Manager，客户现场常称 SCCM 或 MECM）」。版本、生命周期、受支持操作系统一律以核查锚点为准，正文不写具体值。文中「拠点（拠点，即分支站点）」「波次（ウェーブ）」「试点（パイロット）」「回退（切り戻し）」「资产台账（資産台帳）」按此含义使用。

## 3.1 概念模型

配置管理器的客户端行为几乎全部由下面六个概念决定。方案书里用错其中任何一个，客户的技术承认者会立刻判断为「不懂产品」。

### 边界（境界）

- 定义：一条网络位置描述，回答「这台客户端现在在哪里」。类型有 IP 子网、IP 地址范围、目录服务站点、IPv6 前缀；较新版本另有 VPN 类型，可用类型以锚点 AN-01 核实的版本为准。
- 要点：边界本身不产生任何行为。边界只有被放进边界组才生效。
- 用错会怎样：
  - 用 IP 子网类型描述被超网汇总的网段时，客户端按自身子网掩码计算出的子网 ID 与边界不一致，客户端被判定为「不在任何边界内」。拠点网段规划不规整时优先用 IP 地址范围。
  - 用目录服务站点类型时，若客户的目录服务站点只建了总部一个，所有拠点都会被判为总部位置，内容全部从总部分发点拉取。
  - 同一网段同时出现在两个用于站点分配的边界组里，客户端被分配到哪个站点不可预测。

### 边界组（境界グループ）

- 定义：边界的集合，同时规定两件事：这些位置上的客户端「归属哪个站点」（站点分配，サイトの割り当て）与「从哪些站点系统取内容和策略」（内容定位，コンテンツの場所）。
- 必须明确的硬规则：**边界组须同时启用「用于站点分配」与「用于内容定位（关联站点系统）」，才有预期行为。** 只建边界组、不勾站点分配，自动站点分配会失败，客户端装上但不汇报；只做站点分配、不关联分发点和管理点，客户端会回退到默认站点边界组或从远端取内容。
- 边界组关系与回退：边界组之间可以配置邻接关系和回退延迟时间。不配置时，当前边界组内找不到内容就会退到默认站点边界组。默认站点边界组里如果关联了总部分发点或云分发点，拠点客户端就会跨广域网或经公网拉内容。
- 用错会怎样：拠点客户端报告「成功」，但实际下载走的是总部或公网，月末广域网线路被占满，业务系统变慢，客户首先怀疑的是网络部门而不是我们。

### 站点系统角色（サイトシステムの役割）

| 角色 | 作用 | 用错会怎样 |
|---|---|---|
| 站点服务器 | 站点的控制中枢，执行推送安装、处理数据 | 推送账号、发现方法配错，推送静默跳过 |
| 站点数据库 | 保存全部资产、状态、部署数据 | 容量与备份未设计，故障后资产与部署历史全部丢失 |
| 管理点（管理ポイント） | 客户端取策略、交状态的唯一入口 | 未发布到 DNS 或目录服务，客户端找不到站点 |
| 分发点（配布ポイント） | 提供安装源与软件内容 | 拠点未就近配置，内容跨广域网或走公网 |
| 软件更新点 | 与更新服务同步补丁目录 | 代理未配置，同步失败，补丁部署全线停摆 |
| 回退状态点（フォールバックステータスポイント） | 接收尚未分配站点的客户端发来的安装状态 | 不配置时，「装了但不汇报」的客户端完全不可见，排障只能逐台登录查看 |
| 云管理网关（クラウド管理ゲートウェイ） | 让不在内网的客户端连回站点 | 证书与代理设计不全，外出设备长期失联 |

回退状态点在很多项目里被省略。它在铺装阶段的价值最高：它是唯一能从服务端看到「客户端已安装但尚未完成站点分配」这一状态的通道。项目 A 建议在铺装期内必配。

### 集合（コレクション）

- 定义：一组设备或一组用户，回答「对谁做」。成员规则有直接规则、查询规则、包含规则、排除规则，并且每个集合都有一个限定集合（制限コレクション），成员不可能超出限定集合的范围。
- 设备集合与用户集合是两种对象。向用户集合发强制部署，软件会装到该用户登录过的、被判定为其主要设备的任何机器上；向设备集合发部署，与谁登录无关。
- 用错会怎样：
  - 查询规则用名称前缀模糊匹配，命中了同名前缀的服务器或工控终端。
  - 限定集合选了全部系统，排除规则遗漏了服务器，强制部署直接落到服务器上。
  - 本应面向设备的部署挂到了用户集合，共享终端和会议室终端被装上个人用软件。
  - 增量更新未启用时，新客户端要到下一次全量评估才进入集合，铺装验证会误判为「未生效」。

### 部署（展開）

- 定义：把「做什么」（应用、软件包、补丁、配置基线、任务序列）在「什么时候」「以什么用户体验」交给一个集合。
- 关键属性：目的（强制 / 可用）、可用时间与截止时间、截止时间以客户端本地时间还是协调世界时解释、是否允许在维护时段（メンテナンス期間）外安装和重启、用户通知方式。
- 用错会怎样：截止时间已过的强制部署，对新加入集合的客户端会立刻执行。这是铺装期间最隐蔽的事故源：客户端铺装本身不重启，但它一接入就继承了集合上挂着的旧部署，结果在上班时间重启。

### 服务定位（サービスの場所）

- 定义：客户端寻找管理点的机制。来源依次包括：安装时指定的参数、目录服务中发布的站点信息（需扩展架构并授权站点服务器写入）、DNS 中发布的服务定位记录、已缓存的管理点列表。
- 要点：目录服务架构未扩展、也未在 DNS 发布管理点的环境里，客户端只能靠安装参数找到站点；参数漏写即失联。
- 用错会怎样：跨林、工作组设备、或与站点不同 DNS 后缀的拠点，客户端解析不到服务定位记录，表现为「客户端服务正在运行但控制台里看不到它」。

### 六个概念的关系（写方案书时的一句话版本）

边界说明「你在哪」，边界组说明「在那里你归谁、从哪取东西」，站点系统角色是被取用的服务，服务定位是客户端找到这些服务的方法，集合说明「对谁」，部署说明「做什么、何时、怎样打扰用户」。客户端不汇报，查前四个；误推和意外重启，查后两个。

## 3.2 客户端铺装方式与取舍

方案书必须对四条路径做显式取舍，并写出「采用哪条、不采用哪条、理由」。实务上通常是组合：存量机用推送或组策略，新机用镜像，拠点漏网机用登录脚本兜底。

| 路径 | 适用前提 | 制约 | 影响面 | 回退难度 |
|---|---|---|---|---|
| 客户端推送安装（クライアントプッシュインストール） | 设备已加入域、从站点服务器网络可达、推送账号在目标机有本地管理员权限、目标机已被发现 | 依赖管理共享、SMB 与 RPC 通道；拠点防火墙和个人防火墙常拦截；离线设备推不到 | 由服务端主动发起，范围由发现结果和推送设置决定。启用「全站点自动推送」时，范围是所有被发现的设备，包括你不想装的 | 低到中。可随时停止推送；但已安装的需另行卸载。若自动推送不关，卸载后会被重新推上 |
| 软件分发 / 登录脚本触发 | 推送通道打不通的拠点；用户每天登录域；或已有其他软件分发工具 | 登录脚本以用户身份运行，普通用户无管理员权限时需用计划任务或启动脚本提权；依赖用户开机登录 | 仅限实际登录的用户机。影响时点落在登录高峰（上班开机），会与业务系统启动争抢资源 | 中。需从脚本中移除调用，并确认没有缓存副本继续执行 |
| 组策略或 Intune 引导 | 已有成熟的域组策略体系，或设备已纳入 Intune 管理（共同管理场景） | 组策略软件安装依赖开机时的网络与组策略处理；Intune 引导依赖设备已注册云侧且网络可达云端点 | 由组织单位或云侧分组决定范围，组织单位结构不规整时范围难以精确控制 | 中。撤销策略不会自动卸载客户端，需单独卸载步骤 |
| 镜像预装 | 新装机、换机、重装场景；客户有标准镜像流程 | 镜像中的客户端必须在封装前清除唯一标识，否则所有出厂机共用同一标识（见 F-016）；覆盖不了存量机 | 只影响新机，对现有业务零干扰 | 低。重新封装镜像即可；已出厂的机器按卸载流程处理 |

取舍判断的三个问题：

1. 推送通道（管理共享、SMB、RPC）在每个拠点是否都能打通？打不通的拠点必须单独指定路径，不能在方案书中笼统写「推送安装」。
2. 本地管理员权限由谁持有？若客户已用本地管理员密码轮换工具，推送账号的设计要与之协调，否则推送账号会在轮换后失效。
3. 有没有不能装客户端的设备（工控、医疗、收银、共享终端）？这些设备必须在集合与发现层面被排除，而不是期待「推不上就算了」。

写方案书时的句式：「存量设备采用客户端推送安装，不采用登录脚本。理由为：本项目全部拠点的管理共享与 RPC 通道已在 G-A-01 中验证可达。若某拠点验证不通过，该拠点改用启动脚本方式，并在第 7 章波次表中单独标注。」

## 3.3 前置检查清单

与 Gate G-A-01 七项一一对应。任一项不通过，不得进入正式波次。判定必须可复现：每项都要留下导出文件或截图作为证据，附在试点验证报告里。

### G-A-01-1 管理共享可访问

- 为什么需要：推送安装的第一步是站点服务器把安装引导程序复制到目标机的管理共享（管理共有）。共享不可达，推送不报错地停在重试队列里。
- 如何验证：从站点服务器以推送账号身份，对每个拠点抽样（每拠点不少于 3 台、覆盖每种机型和每种操作系统）访问目标机管理共享，记录成功与失败清单。
- 不通过的症状：推送状态长期停留在「重试中」；回退状态点无记录；目标机上没有安装日志目录。
- 修复动作：通过组策略恢复管理共享（确认没有加固策略禁用了它）；放通 SMB（445）；确认文件和打印机共享相关防火墙规则在域配置文件下已启用。

### G-A-01-2 目录服务所需 RPC 与共享通道已放通

- 为什么需要：推送安装需要 RPC 端点映射（135）、动态 RPC 高位端口段、SMB（445），客户端安装后与管理点通信需要 HTTP（80）或 HTTPS（443）及客户端通知通道。拠点之间常有中间防火墙，规则只为业务系统放通。端口清单需按官方端口清单逐项核对，本节列出的端口不是完整清单。
- 如何验证：从站点服务器到每个拠点抽样终端做端口探测；同时导出客户端个人防火墙的组策略，核对入站规则；从拠点终端反向探测管理点与分发点端口。
- 不通过的症状：推送超时；客户端装上后策略获取失败；远程控制和即时通知不可用。
- 修复动作：向网络部门提交端口放通申请，申请单列明源、目的、端口、用途、有效期；个人防火墙规则通过组策略下发，不要求拠点手工配置。

### G-A-01-3 边界组覆盖目标全部网段

- 为什么需要：边界组漏一个网段，那个网段上的客户端就不会被自动分配站点，也不会就近取内容。
- 如何验证：取三份清单做差集：网络部门的网段台账、DHCP 作用域清单、配置管理器边界导出。差集中每一行要有结论（补配 / 确认不纳管 / 待确认）。同时核对每个边界组是否启用了站点分配、是否关联了就近分发点与管理点。VPN 地址池和无线网段最容易漏。
- 不通过的症状：客户端装上但不汇报；内容下载走公网或跨广域网；客户端被分配到错误站点。
- 修复动作：补配边界并放入正确边界组；为边界组启用站点分配并关联站点系统；对重叠网段拆分边界组，确保一个网段只属于一个用于站点分配的边界组。

### G-A-01-4 站点系统已在 DNS 正确发布

- 为什么需要：客户端靠服务定位找到管理点。目录服务架构未扩展、跨林、或工作组设备时，DNS 中的服务定位记录是唯一自动途径。
- 如何验证：从每个拠点的抽样终端解析管理点的服务定位记录和管理点主机名；正向与反向解析都要成功；核对拠点使用的 DNS 服务器是否能解析站点所在区域。
- 不通过的症状：客户端找不到管理点，客户端服务在运行但控制台无记录；安装日志反复出现「无法定位管理点」。
- 修复动作：在站点配置中启用向 DNS 发布管理点；或扩展目录服务架构并授权站点服务器写入系统管理容器；短期补救是在安装参数中显式指定站点代码与管理点。

### G-A-01-5 推送账号在目标机具备本地管理员权限

- 为什么需要：推送安装以推送账号身份在目标机创建服务，没有本地管理员权限就无法安装。
- 如何验证：核对向本地管理员组加入推送账号所属安全组的组策略（受限组或首选项）是否作用于全部目标组织单位；每拠点抽样登录确认组成员；确认推送账号未被「拒绝从网络访问」类加固策略拦截；确认账号密码未过期、未被锁定。
- 不通过的症状：推送安装失败，错误为拒绝访问；同一拠点部分机器成功部分失败（组织单位不同、策略未覆盖）。
- 修复动作：用专用安全组授予权限，不用域管理员账号做推送账号；补齐组策略作用范围；推送账号设为密码不过期但纳入定期轮换流程，轮换前通知交付方更新站点配置。

### G-A-01-6 集合成员规则已复核（含排除项）

- 为什么需要：铺装期间每一个部署都挂在集合上，集合成员算错就是误推，误推在生产环境就是事故。
- 如何验证：导出每个铺装用集合与每个已有强制部署目标集合的成员数，与波次表的预期终端数比对，差异超过 2% 必须逐台解释；抽查排除规则是否覆盖服务器、工控终端、共享终端、VIP 终端；列出这些集合上已有的全部强制部署（见 F-025）。
- 不通过的症状：成员数与预期不符；集合里出现服务器或不应纳管的设备；新客户端加入后立即执行旧部署。
- 修复动作：铺装用集合只用直接规则或经评审的查询规则；限定集合使用「仅工作站」类集合，不用全部系统；排除集合单独维护并有负责人；高风险强制部署设置部署验证阈值。

### G-A-01-7 试点拠点验证报告已出具

- 为什么需要：试点报告是客户决裁者批准大面积铺装的书面依据。没有它，第一次出问题客户就会叫停整个项目，并要求补交报告，往返两三周。
- 如何验证：报告文件存在，且包含：安装成功率、汇报率、健康检查通过率、内容来源分布（本地分发点占比）、工单数与内容、发现的问题与处置结果、对后续波次的设计调整。每项有数据，不接受「良好」类定性描述。
- 不通过的症状：报告缺数据项；客户在大面积铺装中途叫停。
- 修复动作：补采数据并重开试点评审；数据不足时延长试点观察期，而不是带着缺口进入下一波。

## 3.4 失败模式库

每条为「症状 → 根因 → 验证 → 处置」四段式。ID 与跨项目失败模式库共用，实施手册的 `on_fail` 直接引用。

#### F-010 部分拠点内容从公网下载

- 症状：拠点客户端安装与软件部署都显示成功，但拠点出口线路或公网出口在铺装时段流量骤增；网络部门报告业务系统变慢；内容来源统计中「云」或「微软更新」占比异常。
- 根因：拠点网段未被边界组覆盖，或所在边界组未关联就近分发点，客户端回退到默认站点边界组；默认站点边界组关联了云分发点；软件更新部署启用了「当前位置无内容时从微软更新下载」选项。
- 验证：在客户端内容传输日志中查看实际下载源；导出该拠点网段与边界组的对应关系；检查默认站点边界组关联的站点系统；检查补丁部署的下载选项。
- 处置：补配拠点边界并关联拠点分发点；默认站点边界组只保留不会造成广域网冲击的站点系统，或不关联任何分发点；关闭补丁部署的公网回退选项，或明确限定为仅限有云直连的拠点；必要时启用点对点缓存（ピアキャッシュ）。
- 相关 Gate：G-A-01

#### F-011 集合规则误判导致误推

- 症状：软件被装到了不应安装的设备上，常见是服务器、工控终端、会议室共享终端；或用户反映「我没申请的软件装上了」。
- 根因：查询规则按名称前缀模糊匹配，命中了同前缀的设备；限定集合过宽且排除规则遗漏；设备导向的部署挂到用户集合，软件随用户登录到达共享终端；把「可用」与「强制」混淆。
- 验证：导出误推设备的集合成员关系，回溯是哪条规则使其入组；核对部署目的与目标集合类型；在部署前用成员数比对预期数。
- 处置：立即禁用该部署（不是删除，保留记录便于追溯）；将误推设备加入排除集合；评估已安装软件是否需卸载并取得客户同意；集合规则改为评审制，强制部署启用部署验证阈值；面向设备的软件只挂设备集合。
- 相关 Gate：G-A-01

#### F-012 客户端安装成功但不上报

- 症状：终端上客户端服务在运行，安装日志显示成功；控制台中该设备不存在，或显示为「非客户端」；回退状态点有安装成功记录但没有后续心跳。
- 根因：客户端所在网段不在任何启用站点分配的边界组内，自动站点分配失败；管理点未在 DNS 或目录服务中发布，客户端找不到管理点；站点设置要求手动批准客户端而无人批准；HTTPS 模式下证书不满足要求（见 F-015）。
- 验证：在客户端查看已分配站点代码，为空即站点分配失败；查看客户端位置服务日志中的管理点查找结果；从该终端解析管理点服务定位记录；在控制台查看客户端批准状态。
- 处置：补配边界组并启用站点分配；在 DNS 发布管理点或扩展目录服务架构；补救性重新分配站点（客户端控制面板或带站点代码参数重装）；批准待批准客户端，并决定是否改为自动批准域内设备。方案书第 8 章必须为此单列「装上了但不汇报」专项小节。
- 相关 Gate：G-A-01

#### F-013 推送安装超时或失败

- 症状：推送状态长时间停留在重试中；错误为网络路径找不到、RPC 服务器不可用、拒绝访问；同一拠点批量失败。
- 根因：管理共享被加固策略禁用；拠点防火墙未放通 SMB（445）、RPC（135）与动态 RPC 端口段；目标机个人防火墙拦截；推送账号无本地管理员权限；目标机名称解析到了旧地址（DNS 老化未清理）。
- 验证：从站点服务器以推送账号访问目标机管理共享；端口探测；查看站点服务器上的推送安装日志对应目标机的错误码；核对目标机名称解析结果与实际地址。
- 处置：放通端口并通过组策略下发个人防火墙规则；恢复管理共享；补齐推送账号权限；清理 DNS 过期记录；对短期打不通的拠点改用启动脚本路径，并在波次表中标注。推送失败的机器会在后台按小时重试数天，重试队列积压时先清理失效对象再重推。
- 相关 Gate：G-A-01

#### F-014 客户端与服务端版本不兼容

- 症状：部分客户端功能不可用，控制台显示客户端版本参差；站点升级后旧客户端策略处理异常；用镜像带入的客户端比站点版本还新。
- 根因：站点已升级但客户端自动升级未启用；镜像中封装的是预发行或更新版本的客户端；从别的站点或旧环境迁入的设备保留旧客户端。客户端版本高于站点版本不受支持。
- 验证：按客户端版本分组统计数量；核对站点版本与 AN-01 中的支持状态；检查自动客户端升级设置与预生产客户端设置。
- 处置：启用自动客户端升级并设定合理的升级窗口；镜像中的客户端与站点版本对齐，或改为装机后再由站点推送；在第 11 章运维条目中写明「站点升级后客户端升级的确认步骤」。
- 相关 Gate：G-A-01

#### F-015 客户端健康状态异常（证书与信任）

- 症状：客户端显示为不活跃或健康检查失败；HTTPS 或增强型 HTTP 环境下客户端与管理点通信报证书错误；拠点客户端时好时坏。
- 根因：PKI 模式下客户端证书未自动注册或模板用途不符；客户端不信任站点使用的自签名证书或企业根证书未下发到工作组设备；吊销列表发布点从拠点不可达，吊销检查失败；终端时钟偏差使证书被判为未生效或过期。
- 验证：在客户端查看证书存储中的客户端证书与信任链；查看客户端证书选择与通信日志的错误；从拠点终端访问吊销列表发布点；比对终端时间与域时间源。
- 处置：修正证书模板与自动注册策略；将根证书通过组策略分发到全部终端，工作组设备纳入单独分发手段；确保吊销列表发布点拠点可达，或在评估后调整吊销检查设置并记录理由；修复时间同步。健康检查修复动作每天执行一次，修复后需至少一个周期才能确认。
- 相关 Gate：G-A-01

#### F-016 双启动、共享设备与克隆导致资产重复或合并

- 症状：控制台中同名设备有两条记录；或者相反，多台不同设备被合并成一条，资产数量少于实际；集合成员数忽多忽少。
- 根因：双启动设备的两个系统各自注册客户端；镜像封装前未清除客户端唯一标识和证书，所有克隆机共用同一标识；多台设备共用同一 USB 网卡或扩展坞，硬件标识相同被判定为同一设备；冲突记录处理设为自动合并。
- 验证：导出重复名称与重复硬件标识清单；检查镜像制作手册是否包含清除客户端标识的步骤；统计共用扩展坞的型号；核对层级设置中的冲突记录处理方式。
- 处置：镜像封装前执行清除客户端标识的标准步骤，重新封装；把共用网卡和扩展坞的硬件标识加入重复硬件标识排除清单；冲突记录处理改为手动并指定审核人；清理错误记录后让受影响客户端重新生成标识。
- 相关 Gate：G-A-01

#### F-017 老旧操作系统不支持当前客户端

- 症状：特定机型或部门的安装持续失败；安装日志报前置组件缺失或签名校验失败；即使装上也无法获取策略。
- 根因：目标机操作系统已不在当前客户端支持矩阵内；缺少代码签名哈希算法更新或运行库前置组件；该部门出于业务系统兼容原因长期未升级。
- 验证：从现状盘点中按操作系统版本统计台数，逐项对照锚点 AN-02（锚点位于本条末尾）；对失败机检查前置组件安装状态。
- 处置：不受支持的设备在方案书中列为「范围外」，并写明替代措施（升级计划、隔离、单独管理工具）；不允许为凑覆盖率在不受支持系统上强装；可补前置组件的，先由软件分发补齐再装客户端。
- 相关 Gate：G-A-01

#### F-018 现状盘点数据与资产台账不一致

- 症状：配置管理器发现的设备数与客户资产台账相差明显；波次表的终端数与实际推送对象数不符；验收时覆盖率分母无法达成一致。
- 根因：目录服务中残留大量已报废设备的计算机账户；台账未登记私自接入或借用的设备；主机名重用使台账与实际设备对不上；离线设备、长期出差设备不在发现范围内。
- 验证：三方差集：资产台账、目录服务计算机对象（附最后登录时间戳）、配置管理器发现记录。每个差集分类为「报废未删」「在用未登记」「离线」「命名冲突」四类。
- 处置：在第 3 章写明盘点基准日和差集结果，并与客户书面确认覆盖率的分母口径（以台账为准还是以在用设备为准）；残留账户清理由客户执行，交付方只提交清单；超过约定天数未登录的设备不进入铺装集合。
- 相关 Gate：G-A-01

#### F-019 防病毒或 EDR 拦截安装

- 症状：安装中途失败或安装后客户端组件被隔离；部分拠点成功、部分失败，差异与防病毒策略分组一致；客户端运行后 CPU 占用持续偏高。
- 根因：防病毒或 EDR 将安装引导程序、客户端缓存目录、WMI 操作判定为可疑行为；客户端扫描与防病毒实时扫描相互触发。
- 验证：在安装失败时段检索防病毒管理控制台的拦截记录；对比同一机型在不同防病毒策略组下的结果；核对已配置的排除项与官方推荐排除清单。
- 处置：按官方推荐排除清单配置排除项，排除范围由客户安全部门审批并记录；排除策略先在试点拠点生效，确认无拦截后再推广；在第 8 章写明「排除项变更属于安全变更」，需走客户的安全变更流程，预留审批时间。
- 相关 Gate：G-A-01

#### F-020 代理环境导致外网内容获取失败

- 症状：补丁目录同步失败；云分发点、云管理网关或 Intune 相关连接失败；用户浏览器能上网，客户端却连不上外部服务。
- 根因：客户端和站点服务以系统账户运行，不读取用户的浏览器代理设置；代理要求用户认证，系统账户无法通过；代理对特定端点做了 TLS 检查，破坏证书链。
- 验证：在站点服务器和客户端检查系统级代理设置；查看补丁同步日志的错误；向客户网络部门确认代理的认证方式与 TLS 检查例外清单。
- 处置：在站点系统角色上配置代理并使用专用服务账户；为系统账户配置系统级代理或在代理侧对相关端点做认证例外；需要的出站端点按官方清单编制，逐项列明用途和是否经代理，作为安全审查材料提交。
- 相关 Gate：G-A-01

#### F-021 波次排期与拠点业务日历冲突

- 症状：拠点在铺装当天提出「今天不能动」；工厂、仓库、门店拠点在铺装窗口内处于盘点或生产高峰；投诉集中在某几个拠点。
- 根因：波次表只按总部日历排期，没有收集拠点自己的业务日历（業務カレンダー）；忽略了日本商务节奏中的高风险时段：三月末与九月末的期末、八月中旬长连休、年末年初作业冻结；拠点有自己的停机日与盘点日。
- 验证：波次表定稿前，向每个拠点负责人收取业务日历并书面确认；用日历校验脚本校验波次时间窗。
- 处置：波次表中每波注明「拠点已确认日」；与拠点高峰重叠的波次后移，不压缩观察期补回；冲突拠点从当前波次中拆出，归入后续波次。
- 相关 Gate：G-A-01

#### F-022 时区与区域设置导致策略异常

- 症状：海外拠点的部署提前或延后数小时执行；维护时段不生效或在当地上班时间打开；检测脚本在部分终端判断错误。
- 根因：部署截止时间选用了协调世界时，而维护时段按客户端本地时间解释，两者混用；海外终端时区设置错误；检测方法或脚本依赖日期格式或本地化的组名、路径名，在不同区域设置下解析失败。
- 验证：导出部署和维护时段的时间解释方式；抽查海外终端的时区；在日文、英文、其他语言系统上分别运行检测脚本。
- 处置：方案书中统一规定「所有时间按客户端本地时间解释」或「全部按协调世界时」，不混用，并在实施手册中逐项标明；时区不同的拠点单独建集合、单独排维护时段；检测脚本使用与区域无关的标识（安全标识符而不是组名，固定格式而不是本地日期字符串）。
- 相关 Gate：G-A-01

#### F-023 卸载不彻底导致重装失败

- 症状：重装后客户端沿用旧标识，与控制台中已删除的记录冲突；重装报错已存在；客户端被重装后指向旧站点代码。
- 根因：卸载只删了服务，残留了 WMI 命名空间、客户端配置文件中的旧标识、证书、计划任务；或人工删除文件夹代替正规卸载；旧站点信息仍在目录服务中发布。
- 验证：卸载后检查客户端服务、安装引导服务、WMI 命名空间、客户端证书是否全部清除；重装后核对客户端标识是否为新生成。
- 处置：只用客户端安装程序的卸载参数执行卸载，并以脚本验证上述残留项；需要重新生成标识时，按官方步骤处理而不是手工删注册表；旧站点退役前先撤销其在目录服务中的发布。卸载与验证步骤写入实施手册，不允许现场即兴操作。
- 相关 Gate：G-A-01

#### F-024 维护时段配置不当导致业务时间重启

- 症状：用户在上班时间被强制重启；或者相反，部署一直显示「维护时段未到」永远不执行。
- 根因：目标集合未设维护时段，强制部署在截止时间立即执行并重启；设备同时属于多个集合，各集合的维护时段取并集，实际可执行时间比设计宽；维护时段短于部署的最长运行时间，部署永远排不进去；部署勾选了「允许在维护时段外重启」。
- 验证：对抽样终端查看其所有生效的维护时段（并集）；核对每个部署的最长运行时间与维护时段长度；检查部署的维护时段外行为选项。
- 处置：所有铺装波次集合在铺装前设好维护时段，并在第 7 章写出每个拠点的维护时段；维护时段长度大于部署最长运行时间加重启时间；不勾选维护时段外重启；客户端设置中配置重启倒计时与用户通知，给用户留出保存工作的时间。
- 相关 Gate：G-A-01

#### F-025 新客户端继承既有强制部署

- 症状：客户端铺装本身顺利，但铺装后数十分钟内大量终端开始安装软件或补丁并重启；服务台电话集中在铺装当天。
- 根因：环境中已存在面向宽泛集合（全部系统、全部工作站、按操作系统查询的集合）的强制部署，截止时间早已过去。新客户端一加入集合，立即补执行全部积压的部署。
- 验证：铺装前导出所有强制部署及其目标集合，标出铺装对象会落入的集合；按每台新客户端计算会被触发的部署清单和预计下载量。
- 处置：铺装波次期间对相关部署设置维护时段或暂时把铺装对象排除；把「客户端铺装」与「首批软件和补丁下发」拆成两个独立的变更，前者完成观察后再开始后者；在用户侧动作说明中明确告知首批补丁的时间。
- 相关 Gate：G-A-01

#### F-030 运维移交不完整导致上线后问题积压

- 症状：项目结束后，客户运维团队无法处理「不汇报」「健康检查失败」类工单，问题持续积压；站点升级无人执行，支持期临近才被发现；排除集合无人维护，误推复发。
- 根因：移交只交了设计书，没有交操作手顺、监控项和判断阈值；客户运维人员未参与试点与波次作业；没有定义移交完成的判定标准。
- 验证：移交前用移交检查表逐项确认：日常监控项（客户端活跃率、健康检查通过率、内容来源分布、推送失败队列）、阈值和处置手顺、站点升级手顺与频率、排除集合维护负责人、证书到期清单、推送账号轮换手顺。由客户运维人员独立完成一次「不汇报」排查演练。
- 处置：将客户运维人员编入最后两个波次的作业；移交完成标准写入第 11 章并由客户签字；设置移交后的并行支援期，期间工单由双方共同处理并记录。
- 相关 Gate：G-A-01

## 3.5 分阶段铺装设计方法

### 波次划分原则

1. 第一波永远是客户信息系统部门自己（第 0 波）。他们最能描述问题、最能忍受问题，也最能在客户内部证明「我们自己先用了」。
2. 按拠点划分为主，按部门和设备类型为辅。拠点决定网络条件和现场支持，是故障的主要分界；部门决定业务影响；设备类型决定兼容风险。
3. 每一波只引入一种新的不确定性。新网络类型（首个低带宽拠点、首个海外拠点、首个 VPN 群体）、新设备类型（首批笔记本、首批共享终端）不放在同一波。
4. 波次规模逐步放大，每波约为上一波的 3 至 5 倍。规模上限由服务台承受能力决定：每波上限 = 服务台每日可额外处理的工单数 × 观察期天数 ÷ 预期工单率。例：每日可多处理 10 件，观察 3 天，预期工单率 5%，则单波上限约 600 台。
5. 高敏感设备（经营层、财务结算、工厂控制相邻终端）放在较晚的波次，方法稳定后再动，并单独确认时间窗。
6. 每波在第 7 章拠点别铺装波次表中写清：拠点、终端数、时间窗、业务影响、退出条件、拠点已确认日。

### 试点拠点选择标准

试点拠点要能代表「最难的那一类」，而不是「最容易成功的那一个」。选择时逐项打分：

| 标准 | 理由 |
|---|---|
| 网络条件具有代表性（含低带宽广域网线路） | 能暴露内容来源和带宽问题；只在总部试点会漏掉 F-010 |
| 设备构成覆盖主要机型和操作系统版本 | 能暴露 F-016、F-017 |
| 有可配合的现场联系人 | 出问题当天能确认现象，否则试点报告缺数据 |
| 防病毒与防火墙策略与多数拠点一致 | 结论可推广 |
| 试点期间不在业务高峰 | 避免把业务压力误认为铺装问题 |
| 终端数适中（约占总数的 2% 至 5%） | 太少统计无意义，太多出问题影响过大 |

方案书第 5 章要写「为何选它、代表性在哪」，并写明「若试点不通过：暂停后续波次，修正设计后在同一拠点重做试点，不更换试点拠点以规避问题」。

### 每波退出条件

退出条件必须是可测量的阈值，在波次开始前写进方案书，不在事后讨论。建议基准（与客户协商后定值）：

- 安装成功率：在线可达设备中不低于 98%，失败设备逐台有原因。
- 汇报率：铺装后 72 小时内，客户端活跃且完成首次硬件清单上报的比例不低于 95%。
- 健康检查通过率：不低于 95%。
- 内容来源：本拠点分发点或点对点缓存提供的内容占比不低于 95%，公网来源为零或有书面例外。
- 业务影响：无一级、二级事故；服务台工单率不超过事先约定值。
- 遗留项：未达标设备有清单、负责人、处置期限。

任一项不达标，不进入下一波。达标判定由交付方与客户技术承认者共同签字。

### 波次间观察期长度

- 普通波次：5 至 7 个工作日。依据：
  - 观察期必须覆盖至少一个完整业务周，包含周一早晨开机高峰，因为登录高峰时的策略评估和内容下载是最容易暴露带宽与性能问题的时刻。
  - 硬件清单默认周期按天计（具体周期以客户站点设置为准），观察期要至少覆盖一次完整清单周期，汇报率才可信。
  - 客户端健康检查每日运行一次，修复后需再经过一个周期确认，至少需要两到三天。
- 试点波次：10 至 14 个工作日。试点还要额外覆盖一次补丁或软件部署的完整周期，并给出出报告和客户评审的时间。
- 跨越长连休或期末冻结的波次：观察期不得计入冻结期，冻结结束后重新计算至少 3 个工作日。

## 3.6 影响与中断评估方法

客户真正担心的是「明天上班电脑会不会坏」。第 7 章必须用数字回答这个问题。

### 估算用户可见中断

逐项估算，汇总为每拠点一行：

| 影响项 | 估算方法 | 用户可见程度 |
|---|---|---|
| 客户端安装本身 | 按试点实测的安装时长与 CPU、磁盘占用 | 低。通常不需重启，后台安装期间性能略降 |
| 内容下载对拠点线路 | 拠点下载量 = 单机安装源体积 × 拠点终端数（无点对点缓存与本地分发点时）；所需时间 = 下载量 ÷（线路可用带宽 × 允许占用比例） | 中。线路被占满时业务系统变慢 |
| 首次策略与清单上报 | 按试点实测的首次评估耗时 | 低 |
| 继承的既有部署（F-025） | 按铺装对象会落入的集合，列出将触发的部署与重启需求 | 高。这是唯一可能导致重启的来源 |
| 安装失败后的现场处理 | 失败率 × 每台处理时长 | 中。需要用户交机或远程协助 |

带宽估算必须用实测值，不用产品标称值。试点阶段记录单机安装源的实际传输量，作为后续波次计算的基准。

### 用户侧动作说明的写法

第 7 章用户侧动作说明须写三件事，并与第 10 章联络路径一致：

1. 用户需要做什么：例如铺装当天下班前保持电脑开机并接入网络；收到重启通知时保存工作。
2. 用户不需要做什么：不需要自己安装、不需要输入密码、不需要重启；如果看到新出现的软件中心图标，属于正常。
3. 遇到问题找谁：服务台的联络方式与受理时间，异常时需要报告的信息（机器名、现象、发生时刻）。

用户说明面向非技术人员，不出现产品术语。由客户以其内部名义发出，交付方只提供原稿。

### 「无感铺装」的设计

目标是用户在铺装当天察觉不到变化。做法：

- 时间窗放在业务时间外，但要求终端开机在线；笔记本占比高的拠点改为业务时间内低带宽后台下载、业务时间外安装。
- 拠点分发点在铺装前完成内容预置，铺装当天只走局域网。
- 启用后台智能传输的带宽限制，限制铺装时段占用的线路比例。
- 客户端设置中关闭铺装期非必要的用户通知，软件中心品牌和文案提前定好。
- 把客户端铺装与首批软件、补丁下发拆成两个变更（见 F-025）。
- 铺装对象所在集合预先设好维护时段，不允许维护时段外重启。
- 不保证零中断。方案书只写「设计目标为用户无需操作、无需重启」，并写明残余风险与对应处置。

## 3.7 回退设计

回退分两级，方案书第 9 章必须分开写，不可混为一谈。第一级是组织动作，第二级是技术动作。大多数问题用第一级即可控制，第二级只在客户端本身被证实造成业务问题时启用。

### 第一级：停止后续波次（组织动作）

- 触发条件（任一满足即触发）：
  - 当前波次退出条件任一项未达标。
  - 发生一级或二级业务事故，且原因与铺装相关或尚未排除。
  - 服务台工单率超过约定上限。
  - 客户拠点负责人或技术承认者书面要求暂停。
- 时间点：
  - 计划性判定在每波观察期结束、下一波开始前一个工作日的波次判定会上做出。
  - 突发事故时，交付方当日内向客户首报，原因未明也要报「已发生、正在调查、下次更新时刻」，暂停判断不以查明原因为前提。
- 动作：禁用下一波的推送与部署；关闭全站点自动推送；冻结铺装用集合的成员变更；通知后续波次拠点延期。
- 完成标准：控制台确认后续波次无任何生效中的推送与部署；全站点自动推送已关闭；延期通知已送达全部相关拠点并有回执；暂停原因、影响范围与恢复条件已形成书面记录。恢复时以重新通过当前波次退出条件为前提。

### 第二级：客户端卸载（技术动作）

- 触发条件：
  - 客户端或其组件被证实与业务应用冲突（在受影响终端上卸载后问题消失，重装后复现）。
  - 安全部门判定客户端存在不可接受的风险。
  - 客户决裁者决定终止项目。
  - 仅「不汇报」或「健康检查失败」不构成卸载理由，这些问题应修复而非卸载。
- 时间点：原则上在当前波次观察期内执行，此时受影响范围最小、终端状态最清楚。观察期结束后的卸载按新的变更申请处理，并单独排期与业务日历核对。
- 前置动作：先关闭全站点自动推送、移除相关组策略或登录脚本、将对象移出铺装集合。否则卸载后客户端会被重新装上。
- 执行：使用客户端安装程序的卸载参数，通过启动脚本或客户端仍可用时的部署下发；卸载后用脚本验证残留项（见 F-023）。
- 完成标准：目标终端上客户端服务与安装引导服务不存在；WMI 命名空间与客户端证书已清除；控制台中对应记录已删除且在一个发现周期后未再出现；没有任何机制会重新安装它；受影响业务应用经用户部门确认恢复正常。
- 必须写明的边界：卸载客户端不会撤销已经通过它安装的软件与补丁。若需要撤销，属于另一项回退，须逐个软件评估。

方案书第 9 章的句式：「若在第 N 波观察期结束时任一退出条件未达成，则启动第一级回退，停止第 N+1 波，暂停判定在下一波开始前一个工作日完成。仅当客户端被证实与业务应用冲突时，启动第二级回退，对受影响终端卸载客户端，单拠点卸载作业预计在一个维护时段内完成。」
